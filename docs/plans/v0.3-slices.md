# v0.3 delivery slices

Status: planned on 2026-09-13

## Goal

v0.3 makes the smallest v0.2 full-stack application pleasant and predictable to work on every
day. It does not broaden the Next.js compatibility claim or pull the portable native-runtime work
from v0.4 forward.

These are capability slices, not promises that every package will share a `0.3.0` version. A slice
is complete only when the reference application demonstrates the capability from packed workspace
artifacts and the affected public contracts have tests and documentation.

## Entry gate owned by v0.2

Planning and isolated protocol work can begin before v0.2 is released. End-to-end v0.3 work starts
from the v0.2 reference application only after it can:

- render a layout, a dynamic page, and a serializable hydrated client boundary;
- execute a Fetch route handler through the Node.js reference runtime;
- complete `new -> dev -> build -> start` from packed packages; and
- reject a server-only or capability-bearing module from browser output with a structured error.

If that gate changes, this plan is revised rather than adding a parallel application model inside
the CLI or generator.

## Delivery rules

1. Every slice advances the same packed reference application and leaves it usable.
2. `pnpm` remains the dependency resolver and script runner. Kunlun may orchestrate it but does not
   implement package resolution, lockfiles, or workspace linking.
3. A dry run performs no filesystem writes, process launches, network calls, or listener startup.
4. Machine output uses versioned schemas and stable diagnostic codes; human output is a renderer of
   the same underlying events.
5. An adapter reports an unsupported capability or a documented fallback instead of claiming
   parity with the reference engine.
6. A public extension hook is not complete without a third-party fixture, lifecycle documentation,
   and a failure diagnostic.

## Slice map

| Slice | User-visible checkpoint | Depends on |
| --- | --- | --- |
| A. Inspectable creation | preview and create the reference app from a versioned template | v0.2 entry gate |
| B. Closed local lifecycle | install, check, and test the created app through one CLI | A |
| C. Machine-readable operations | automate finite and long-running commands without scraping prose | A, B |
| D. Deterministic development feedback | edit routes and modules with honest HMR/reload behavior | B, C |
| E. Coherent application conventions | use error, loading, and metadata conventions in dev and production | D |
| F. Extension and performance gate | extend supported seams and enforce published budgets | C, D, E |

### Slice A — Inspectable creation

**Outcome:** `kunlun create` produces the v0.2 reference application from a first-party versioned
template; `kunlun new` remains a compatibility alias.

Scope:

- define a generator protocol version independently from the CLI package version;
- make template identity, template version, requested builder, planned files, dependency edits, and
  next commands inspectable before execution;
- ship one first-party application template and builder-specific dependency choices;
- reject collisions and invalid destinations before the first write; and
- support `create --dry-run` and `create --json` from the first merge.

Acceptance:

- the same normalized plan drives dry-run output and actual writes;
- plans are deterministic after replacing the absolute destination with a fixture token;
- the generator never mutates a non-empty destination; and
- a project generated from packed packages reaches the v0.2 `dev`, `build`, and `start` path.

Deferred: remote templates, a template marketplace, dependency installation, and migration of
existing applications.

### Slice B — Closed local lifecycle

**Outcome:** from a fresh directory, a contributor can run `create`, `install`, `check`, `test`,
`dev`, `build`, and `start` without learning a second Kunlun-specific lifecycle.

Scope:

- add `install` as an explicit orchestration boundary around the project-declared pnpm version;
- add `check` for config loading, route compilation, capability compatibility, target validation,
  and generated-project invariants;
- add `test` as a delegation point to the generated template's declared test task;
- make child-process arguments visible in dry-run plans and preserve the child exit status; and
- teach `doctor` to distinguish environment, project, builder, runtime, and package-manager
  failures.

Acceptance:

- one clean-room test executes the complete finite path from packed packages;
- running `install` cannot silently switch package managers or rewrite the requested pnpm version;
- `check` performs no production build and starts no listener; and
- each failure has a stable code, remediation, and non-zero exit status.

Deferred: a general task runner, an alternative package-manager abstraction, and remote execution.

### Slice C — Machine-readable operations

**Outcome:** CI and editor integrations can plan and observe every command without parsing human
sentences.

Scope:

- define `kunlun.operation-plan/v1` for inputs, ordered steps, side effects, selected adapters, and
  artifacts;
- define `kunlun.event/v1` JSON Lines for diagnostics and lifecycle events, including long-running
  `dev` and `start` sessions;
- apply `--dry-run` to `install`, `check`, `test`, `build`, `dev`, `start`, and `doctor` wherever a
  meaningful plan exists;
- apply `--json` without mixing banners or progress text into stdout; and
- publish exit-code and diagnostic-code ownership rules.

Acceptance:

- JSON output validates against checked-in fixtures;
- two equivalent invocations emit equivalent plans after documented volatile fields are removed;
- `dev --json` reports ready, invalidated, fallback, error, and stopped states; and
- human and JSON modes are contract-tested from the same internal operation events.

Deferred: remote control protocols and persisted execution history.

### Slice D — Deterministic development feedback

**Outcome:** a source edit produces HMR when the selected engine can preserve state, a deterministic
full reload or server restart when it cannot, or a precise unsupported diagnostic.

Scope:

- classify client, server, convention-tree, configuration, and capability-affecting changes;
- define invalidation and restart lifecycle events above engine-native watchers;
- exercise Nasti and Vite native HMR/SSR hooks and document full-reload behavior for Webpack and
  Rspack until their adapters advertise stronger capabilities;
- cover route addition, removal, renaming, layout edits, route-handler edits, and config edits; and
- make cleanup idempotent after partial startup failures and process signals.

Acceptance:

- a shared fixture matrix records the expected action for each change class and adapter;
- route discovery cannot remain stale after a convention-tree edit;
- fallback behavior is visible in both human and JSON modes; and
- repeated development sessions do not leak ports, watchers, or signal handlers.

Deferred: cross-machine HMR, distributed caches, and false parity across native plugin systems.

### Slice E — Coherent application conventions

**Outcome:** route, layout, error, loading, and metadata behavior is explicit and equivalent in the
development and production paths.

Scope:

- compile error and loading boundaries plus static and generated metadata into inspectable core
  contracts;
- specify inheritance, precedence, serialization, and failure behavior;
- connect convention changes to Slice D's invalidation classes; and
- add development/production conformance fixtures, including malformed and conflicting modules.

Acceptance:

- the reference application demonstrates all five convention families;
- the same route request selects the same boundaries and metadata in development and production;
- unsupported exports and conflicts have source-located diagnostics; and
- no convention implicitly grants a runtime capability or crosses the client boundary.

Deferred: broad Next.js API compatibility, caching, mutations, and a complete React Server
Components surface.

### Slice F — Extension and performance gate

**Outcome:** third parties can use the supported seams without private repository knowledge, and
the release publishes measured costs for the reference workflow.

Scope:

- document and fixture the generator, route compilation, rendering, and build-adapter hooks that
  survived Slices A-E;
- add one out-of-tree-style fixture per public hook and one intentional failure fixture;
- measure cold start, route discovery, incremental rebuild or fallback reload, and generated client
  bytes in controlled CI jobs;
- define hardware/runtime metadata and separate alert thresholds from marketing targets; and
- finish the `create -> install -> check -> test -> dev -> build -> start` release-gate fixture.

Acceptance:

- every supported hook has versioning, lifecycle, cleanup, and diagnostic documentation;
- measurements are reproducible and published with environment metadata;
- regressions outside the agreed tolerance fail the dedicated performance job; and
- the repository-wide v0.3 exit gate passes from packed artifacts.

Deferred: public stability for untested native plugin APIs and any production security claim for
hostile third-party extensions.

## First implementation issue

Start with Slice A's plan-before-write core, not a second hard-coded directory writer. The first
issue should deliver the generator protocol types, normalized plan fixture, collision validation,
and a no-write `kunlun create --dry-run --json` path. File materialization can then become the
executor of that tested plan in the following merge.
